# Changelog

## 1.13.1 — 2026-10-27
- **PhoneAPI can link to Lull.** PhoneAPI's Providers screen opens Lull's own **Let PhoneAPI use Lull?** screen, with two switches, both off: **See** (every `GET`) and **Change** (everything else). On **Allow**, PhoneAPI gets its own key, separate from yours, and the local API switches on. The key travels only as the screen's result, and only to PhoneAPI's release build, checked against its pinned signing certificate; anything else gets nothing. A second link replaces the first key.
- **Lull proves who is listening.** Once linked, every answer to a request carrying `X-PhoneAPI-Challenge` (health, 401s, 404s and errors included) carries `X-PhoneAPI-Proof`, an HMAC of the challenge under a key only Lull and PhoneAPI hold, so another app squatting on port 8787 cannot pass for Lull.
- PhoneAPI's key does only what its switches allow (`403` otherwise); yours is unchanged. **Local API** shows whether PhoneAPI is linked, with **Unlink PhoneAPI**. Uninstalling PhoneAPI, or replacing it with a build not signed by its key, unlinks it.
- Internal: `PhoneApiProof` and `PhoneApiAccess` have no Android imports and are tested on the JVM. 192 tests to **199**.

## 1.12 — 2026-09-16
- **Delete a track from the device.** The last entry on the selection bar — long-press a track, an album, a folder — and a button on the **Now Playing** top bar, because the moment you decide a track has to go is usually the moment you are listening to it.
- **Lull asks before the system does.** On Android 11 and up the platform puts its own confirmation over the app and does the deleting itself, and Lull's dialog still comes first: the system's asks whether you meant to delete *a file*, while Lull's says which track, how many, and that the rating and the playlist entries go too. On Android 9 and below there is **no system dialog at all**, and Lull's is the only thing between a long-press and a file being gone for good.
- **All three of Android's answers to deleting are covered.** API 30+ asks once for the whole batch through `MediaStore.createDeleteRequest` and lets the system do it; API 29 gets a `RecoverableSecurityException` carrying a consent dialog for *one file*, so a selection is worked through a file at a time, which is what Android 10 is; API 26–28 is a plain `WRITE_EXTERNAL_STORAGE` delete, which is why that permission is back in the manifest with `maxSdkVersion="28"` on it.
- **Nothing trusts the result code.** `RESULT_OK` says the user pressed a button, not that every file went — one can be on a card since unmounted, or owned by another app. What actually happened is read back out of MediaStore afterwards, so the toast can say "Deleted 3 of 5" rather than claiming five. An existence check that itself fails answers "they are all still there", because keeping a rating for a track that is gone is a far smaller wrong than throwing away ratings for tracks that are not.
- **Everything keyed to the track goes with it**: the rating, the measured BPM, the loudness profile and its place in every playlist, each in one write for the whole batch. Those stores key on the MediaStore id so a rating survives a file *moving* — but a deleted file is not moving anywhere and a re-added one gets a new id, so this is the single case that overrides the playlists' rule of skipping a missing track rather than pruning it.
- The deleted tracks are taken out of the playing queue, **highest position first**. Removing low-to-high shifts every index after the first removal, so on two adjacent deletions an ascending pass takes out a track the listener never asked to lose — a regression test says so.
- **The API deliberately cannot do this**, and `GET /api/docs` now says so rather than leaving a silent gap. It is the only place Lull breaks its own "everything the API can do, the UI can do" rule, for two reasons: from Android 10 up the system has to ask a person, and a request arriving on a socket while the phone is in a pocket has nobody to ask; and this is the only irreversible thing in the app, so a key that leaks should cost you a scrambled queue rather than a library.
- Internal: the decisions worth being right about are lists, so they are in `Deletion` with **no Android imports** and are tested on the JVM — what went versus what was asked for, pruning playlists, and those descending queue positions. The flow itself (`DeleteFlow`) is one class both screens use, because registering the activity-result launchers and holding a batch across the system's dialogs is identical either way. 171 tests to **183**.

## 1.11 — 2026-09-14
- **Push through quiet parts.** The other half of the dead-spot problem, and the half 1.10 could not reach: Force Tempo sets a speed **per track**, so a quiet piano bridge *inside* a 140 BPM song is still at 140 BPM and 1.10 left it exactly where it was. This finds those stretches and speeds up **further** while you are in one, then eases back out at the end of it.
- Under **Force tempo** in the overflow menu, below the existing settings: a switch, **how much faster** in a quiet part (+10% to +150%, default +50%) and **how quiet counts** (3–24 dB below the track, default 9). Off by default, like everything in Lull that changes what you hear.
- **Measured against the track's own level**, never an absolute one. A quietly mastered song is not one long dead spot and a loud one is not free of them, so the reference is a high percentile of that track's own seconds — not its peak, because a single cymbal crash would otherwise raise the bar for the whole song and turn ordinary verses into dead spots.
- **Three guards against speeding up where it would be vandalism.** A stretch must last **6 seconds** — the bar of held breath before a drop is the *opposite* of a dead spot, and speeding through it would wreck the one moment the track was building to. Two quiet stretches split by a short fill are **one** dead spot rather than two. And every second of a reported section meets the threshold on its own.
- **The speed ramps rather than steps**, over 800ms, and it starts ramping **800ms before** the quiet part does — so it has finished arriving by the time you get there. Beginning the ramp on the boundary would mean the first seconds of the dead spot, the ones most worth skipping, are the ones still played at the old speed.
- **One decode, two answers.** Working out where a track goes quiet needs the *whole* file, unlike the tempo, which needs half a minute from the middle. So the analysis now decodes end to end once and produces both — it is still done once per track, on a background worker, only while the feature is on, and a track ahead of the one you are hearing.
- **What is stored is the loudness curve, not the conclusion** — one byte per second, in its own preferences file. Moving the "how quiet counts" slider therefore re-reads every track already measured instead of invalidating a library, and the panel shows what the current setting finds in the track playing right now, live as you drag it.
- API: `GET /api/tracks/{id}/quiet` lists what was found, and distinguishes **"never analysed"** from **"analysed, nothing there"**; `pushQuiet`, `quietBoost` and `quietThresholdDb` on `/api/settings`; `boosted` on `/api/player`, whose `speed` is now read off the engine rather than recomputed, because with this on the speed moves *during* a track.
- Internal: `BpmDetector` becomes `TrackAnalysis`, since it no longer only detects a tempo. 138 tests to **171**. One of the new ones is a regression: a first cut widened the threshold on the way out of a section, in decibels, which let a run continue through seconds that did not qualify at all — on the device a **4-second dip swallowed the remaining 160 seconds** of the track. Gap-merging already provided the anti-flap property that was meant to buy, without ever including a second that fails the threshold, so the decibel hysteresis is gone.

## 1.10 — 2026-09-14
- **Force Tempo.** Switch it on under **Force tempo** in the overflow menu, set a target — 110, 140, 200, anywhere from 60 to 200 BPM — and every track plays at that tempo. It is a **pitch-preserving** stretch (ExoPlayer time-stretches with Sonic), so a track sped up to reach the target still sounds like itself rather than like a cartoon.
- The reason it exists: a workout playlist where **one slow track is a slow patch in the workout**. So the default is **never slow a track down** — anything already at or above the target is left completely alone — and how far a track may be pushed to reach the target is a second slider, defaulting to **30%**, which is roughly where a stretch stops being unnoticeable.
- **A track's tempo is read from its `TBPM` tag where it has one, and measured from the audio where it does not** — half a minute decoded from 30 seconds in, reduced to an onset envelope and autocorrelated. The answer is remembered per track, so it is worked out once. The *next* track in the queue is analysed while the current one plays, so the only track ever heard at the wrong speed is the one already playing when you switch the feature on.
- **A track with no tempo is never touched.** An audiobook, a drone or a field recording is analysed, found to have no steady beat, and written down as having none — it plays unchanged, and it is not analysed again. That distinction (nothing known yet / nothing there) is carried all the way out to the API.
- **The measured tempo is editable**, because it is a measurement rather than a preference and you can hear when it is wrong: the panel shows the playing track's BPM in a field you can type over, and a number you supply is never quietly re-measured. Clearing it throws the measurement away and has another go. Over the API that is `GET`/`PUT /api/tracks/{id}/bpm`, with `0` to forget it.
- **Octaves are handled rather than ignored**, in two places. A 70 BPM track counted in double time *is* 140, so it is left alone instead of being played at 2.0x — but only where the folded reading lands near the target, so a merely slow 95 BPM track is not excused as a secretly-fast one. And the estimator resolves its own octave twice over: a preference weight around the perceived pulse, and a tie-break that takes the faster reading when the audio supports both equally (a rhythm that repeats every beat also repeats every two, and only one of those is the beat).
- `GET /api/player` now reports the `speed` the playing track is running at and its `source_bpm`; `PATCH /api/settings` takes `forceTempo`, `tempoBpm`, `tempoMaxChange` and `tempoOnlyFaster`. `GET /api/docs` documents all of it.
- Internal: Force Tempo makes **media time and wall-clock time different quantities** for the first time. Crossfade is counted by the clock while a track's remaining duration is counted in the track, so at 1.3x a fade timed against the wrong one starts late and gets cut off; an A-B loop would overshoot B by the same ratio. Both now convert through one tested helper, and a crossfade sets the *incoming* track's own speed before it is heard, so the transition itself has no tempo change in it.
- The suite goes from 83 tests to **138**. Two of the new ones exist because the estimator was wrong when they were written: a whole-frame lag search reads a 160 BPM track as 80 (its beat lands every 37.5 envelope frames, so neither lag 37 nor 38 lines the rhythm up with itself while 75 does), and a uniform 200 BPM rhythm reads as 100 unless the tie-break prefers the beat over the bar. Both were caught on generated click tracks with known tempos, and the second was confirmed on a device.

## 1.9 — 2026-09-13
- **Share button.** Send the playing track from the moon-row on Now Playing, or a whole selection from the library's contextual bar — long-press a track, an album, a folder. **The file itself travels, with its metadata alongside**: title, artist, album, genre, duration, size and your own rating are written into the share text, because a `content://` uri carries none of that and what arrives at the other end is otherwise a filename. Nothing is re-encoded and no tag is rewritten — the file that leaves is byte-for-byte the file on disk.
- Typed as precisely as the extension allows (`audio/mpeg` for an MP3, not the wildcard), since some receivers filter on the concrete type; a mixed selection falls back to the generic one rather than lying about what is in it.
- **A local API.** Turn it on under **Local API** in the overflow menu and Lull generates a key; a script or agent holding that key can do what you can — browse the library, play, queue, seek, skip, set repeat and shuffle (including Favourites), rate, build and reorder playlists, change settings, arm the sleep timer, set an A–B region, and share.
- **Off until you switch it on**, and bound to `127.0.0.1` unless you also turn on LAN access — which says out loud what it changes. The key is generated, never typed, and a new one can be issued at any time. `GET /api/docs` serves the whole reference to whoever is holding the key, so an agent needs nothing but the port.
- **The API's answer to "share the whole track" is `GET /api/tracks/{id}/file`** — the audio, streamed, named. `POST /api/share` pops the real chooser on the device and, crucially, *says whether anyone can see it*: Android does not let a background app throw a dialog over what you are doing, so the response carries the share text and the file urls either way.
- It runs in its own foreground service, separate from playback, with a notification naming the address it is listening on and a Stop action. A socket that is open should never be something you have to go looking for. It comes back after a reboot only if you left it on.
- **This is the version that adds `INTERNET` to the manifest**, because a listening socket needs it even to bind loopback. Lull still makes no outbound connection of any kind and has no analytics, ads or telemetry — but the README no longer claims "no network access", because that would now be a lie by omission.
- Internal: the API is split so that the half worth testing has no Android in it. Request parsing, routing, auth and every error shape live in plain Kotlin behind an `ApiBackend` interface, and are covered by unit tests against a fake — **the suite goes from 5 tests to 82**, including one that walks the route list `/api/docs` advertises and fails if any of it is unrouted.

## 1.8 — 2026-09-11
- **Star ratings.** Rate a track 1–5 from the star row on Now Playing (tapping the star it already sits on clears it), or long-press in the library and rate a whole selection at once. Rated tracks show a compact star strip on their row.
- **A Rated tab**, alongside the other six: five stars down to one, best first. No "unrated" bucket — on a real library it would hold nearly everything and be a second copy of the Tracks tab.
- **Favourites shuffle**, the new third state of the shuffle button (off → shuffle → favourites): **3 stars and up come around early and often**. The weight jumps at three stars rather than creeping, because three is the lowest rating that still means "yes"; an explicit 1 star is rarer than no rating at all, since a low rating is a judgement and no rating is just silence.
- It is a reordering, not a filter — every track you asked for is still in the queue, so Next reaches all of it eventually. Tapping a specific track still plays that track first and weights the rest behind it. Switching it on mid-queue re-weights only what has not played yet and leaves the playing track alone; switching it back off therefore cannot unscramble it.
- Ratings are a map of MediaStore ids in `SharedPreferences`, like playlists: nothing is written to the audio file, and a rating survives the file moving. (MediaStore has no writable rating column for audio.)
- Internal: Media3's `shuffleModeEnabled` is an unweighted permutation with no hook to bias it, so Favourites shuffle builds the queue itself — a one-pass Efraimidis–Spirakis weighted draw — and hands the player a plain queue with shuffle off. `PlaybackService` needed no changes at all.
- The project gains its first unit tests (`./gradlew testDebugUnitTest`), because "higher rated tracks come up first" is a claim about a distribution and one run can neither confirm nor refute it. They caught a real bug before release: drawing the sort key inside `sortedBy` re-randomises it on every comparison, which is an inconsistent comparator — harmless on a short queue, and `IllegalArgumentException: Comparison method violates its general contract!` on a library big enough for TimSort to merge runs.

## 1.7.1 — 2026-09-07
- **Audiobooks are back in the library.** 1.7 narrowed the MediaStore query to `IS_MUSIC` (plus podcasts), and an audiobook has `IS_MUSIC = 0` — so on a device that is mostly spoken word most of the library disappeared. The query now excludes only what nobody wants in a player: ringtones, alarms and notification sounds. Everything else — music, podcasts, audiobooks, recordings — is listed, as it was before 1.7.

## 1.7 — 2026-09-07
- **Open from a file manager.** Lull now appears in "Open with" for audio — `audio/*` plus the `application/ogg`/`flac` types some providers still send, over `content://` and `file://`, with a matching extension filter for senders that give a bare uri and no type at all. It also accepts a share (`SEND` / `SEND_MULTIPLE`), so a selection can go straight to the player.
- Opening **one** track offers its **whole folder**, so Next pages through it. Three routes in order: the `ClipData` the launching app attached (Sift does this — no permission needed, and the only route that works for a `.nomedia` folder), then the folder resolved out of Lull's own library, then the single file. Resolving the folder handles a file manager's private `FileProvider` uri by reading the real path off the open descriptor (`/proc/self/fd/N`), which answers neither a MediaStore id nor a `DATA` column.
- **A launch from another app never waits on media permission.** Without it there is nothing to load, so the intent's own read grant carries the playback; with it, the library load is awaited first so the folder can be built.
- **Folder, Artist, Album and Genre views**, alongside the flat track list and playlists — six tabs, each a list you drill into and Back out of. The tab and the folder/artist/album/genre/playlist you were on are both remembered.
- Genre comes from MediaStore's genre membership tables rather than the `GENRE` column, which only exists from API 30; it is one query per genre, once per load, off the main thread.
- **Multi-selection.** Long-press any row to start it, tap to add more. Play the selection, add it to the queue, add it to a playlist, remove it from the one you are in, or select all. It works on **groups** too — long-press an album or a folder and everything in it comes with it. Selection is held by track id, so it survives a search keystroke or a playlist edit.
- **A real playlist manager.** Playlists are their own tab, with a per-row menu — play, rename, **duplicate**, delete — and a button to make a new one. Adding a selection is one write for the whole batch rather than one per track.
- The selection bar now **overlays** the toolbar instead of stacking above it, which used to push the whole list down the moment a selection started.

## 1.6 — 2026-08-03
- **Sleep timer**: play for 5–90 minutes, fade out over the last 30 seconds, then pause. Set it from the moon button on Now Playing or from the overflow menu; while it runs, the Now Playing title bar counts it down and the overflow entry shows the time left. The countdown lives in `PlaybackService`, so it keeps running with the app closed and the screen off, and it is measured against `elapsedRealtime` so it counts through device sleep rather than stopping with the CPU.
- The fade follows a **raised cosine**, which is flat at both ends — it eases in without an audible step and settles onto silence instead of arriving at it mid-drop. On a short timer the fade is capped at half the total, so a 1-minute timer doesn't spend 30 seconds fading.
- It ends on **pause**, not stop: the queue and your place in it survive, so it's one tap to carry on.
- A running timer is deliberately **not persisted** — restoring a countdown after a restart would be a promise about a device that was switched off. Only the duration you last chose is remembered.
- Internal: crossfade and the sleep timer both want the engine volume, so they now contribute independent gains that are multiplied in one place (`applyVolumes`) rather than overwriting each other. A crossfade is also skipped if the timer would fire before it finished, so the last thing you hear isn't a track you never chose to end on.

## 1.5 — 2026-07-18
- **Playlists**: create, rename and delete playlists, and add or remove tracks. Long-press a track to add it to a playlist (or remove it, from inside a playlist). Playlists are stored as lists of track ids in `SharedPreferences`, so a track that has since been deleted is skipped when the playlist is shown rather than pruned.
- **Reorder**: drag the handle on the right of a row to reorder a playlist; the new order is saved when you drop it. The handle only appears in a playlist view with no active search, where row position maps 1:1 to stored order.
- **Opens where you left off**: the library reopens on the last collection you were viewing — All tracks or a specific playlist. Falls back to All tracks if that playlist was deleted.
- The toolbar title now shows the current collection (the app name for All tracks, otherwise the playlist name). Switch or create playlists from the new Playlists toolbar action.

## 1.4 — 2026-07-12
- **Trim silence** (off by default, in the overflow menu): shortens long stretches of near-silence as they play — dead air inside a track, and the padding at its head and tail. Runs in ExoPlayer's audio sink, below the track transition, so unlike crossfade it does not displace gapless playback; the two compose.
- Note: with Trim silence on, the scrub bar jumps forward over a trimmed gap and a track ends before the bar reaches the end. The position is reported in media time, so this is expected rather than a glitch.

## 1.3 — 2026-07-11
- **A-B loop**: mark two points in a track and loop between them; survives closing the UI.
- **Crossfade** (0–12s, off by default): overlaps the end of one track with the start of the next, on an equal-power curve. Mutually exclusive with gapless; skipped while repeat-one or an A-B loop is active.

## 1.1 — 2026-07-10
- **Mix with other audio**: keep playing without taking audio focus, so a video or a call notification from another app doesn't stop the music.
